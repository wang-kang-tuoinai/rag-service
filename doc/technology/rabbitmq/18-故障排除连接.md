# 排查网络连接问题

## 概述

本指南是对网络连接指南的补充，侧重于网络连接的排查。

对于使用 TLS 的连接，请参考额外的TLS 排查指南。

## 排查方法论

排查网络连接问题是一个宽泛的话题，已有专门的著作论述。本指南旨在介绍一套方法论以及广泛使用的网络工具，帮助用户高效地缩小最常见问题的范围。

网络协议是分层的，相关问题也是如此。有效的排查策略通常采用排除法，从高层开始定位问题（或多个问题）。对于消息传递技术，以下步骤通常既有效又足够：

  * 验证客户端配置
  * 使用 `rabbitmq-diagnostics listeners`、`rabbitmq-diagnostics status` 和 `rabbitmq-diagnostics environment` 验证服务器配置
  * 检查服务器日志
  * 验证主机名解析
  * 验证所使用的 TCP 端口及其可访问性
  * 验证IP 路由
  * 如果需要，获取并分析流量转储（流量捕获）
  * 验证客户端是否能成功进行身份验证



按顺序执行这些步骤，通常有助于找出绝大多数网络问题的根本原因。对于低于互联网（网络）层的排查工具和技术，不在本指南的讨论范围内。

某些问题仅发生在连接频繁变动（connection churn）较高的环境中。可以使用管理 UI 检查客户端连接。还可以检查节点的所有 TCP 连接及其状态。将随时间收集的信息与服务器日志相结合，将有助于检测连接变动、文件描述符耗尽及相关问题。

## 验证客户端配置

开发者和运维人员都遇到过这种情况：拼写错误、过时的配置值、配置工具的问题、公钥和私钥路径混淆等等。第一步是仔细核对应用程序和客户端库的配置。

## 验证服务器配置

验证服务器配置有助于证明 RabbitMQ 正在以预期的网络相关设置运行。这也能验证节点本身是否确实在运行。以下是推荐的步骤：

  * 确保节点正在运行，使用 `rabbitmq-diagnostics status`
  * 验证配置文件位置正确且具有正确的语法/结构
  * 使用 `rabbitmq-diagnostics listeners` 或 `rabbitmq-diagnostics status` 中的 `listeners` 部分检查监听器
  * 使用 `rabbitmq-diagnostics environment` 检查有效配置



请注意，在旧版本的 RabbitMQ 中，`status` 和 `environment` 命令仅作为 rabbitmqctl 的一部分提供：即 `rabbitmqctl status` 等。在现代版本中，可以使用任一工具来运行这些命令，但大多数文档指南通常推荐使用 rabbitmq-diagnostics。

监听器部分看起来如下所示
    
    
    Interface: [::], port: 25672, protocol: clustering, purpose: inter-node and CLI tool communication  
    
    
    Interface: [::], port: 5672, protocol: amqp, purpose: AMQP 0-9-1 and AMQP 1.0  
    
    
    Interface: [::], port: 5671, protocol: amqp/ssl, purpose: AMQP 0-9-1 and AMQP 1.0 over TLS  
    
    
    Interface: [::], port: 15672, protocol: http, purpose: HTTP API  
    
    
    Interface: [::], port: 15671, protocol: https, purpose: HTTP API over TLS (HTTPS)  
    
    
    Interface: [::], port: 1883, protocol: mqtt, purpose: MQTT  
    

在上面的示例中，节点上有 6 个 TCP 监听器

  * 端口 `25672` 上的节点间和命令行工具通信
  * 端口 `5672` 上的非 TLS 连接的 AMQP 0-9-1（及启用时的 1.0）监听器
  * 端口 `5671` 上的 TLS 加密连接的 AMQP 0-9-1（及启用时的 1.0）监听器
  * 端口 15672 (HTTP) 和 15671 (HTTPS) 上的 HTTP API 监听器
  * 端口 1883 上的非 TLS 连接的 MQTT 监听器



在第二个示例中，节点上有 4 个 TCP 监听器

  * 端口 `25672` 上的节点间和命令行工具通信
  * 非 TLS 连接的 AMQP 0-9-1（及启用时的 1.0）监听器，端口 `5672`
  * TLS 加密连接的 AMQP 0-9-1（及启用时的 1.0）监听器，端口 `5671`
  * 端口 15672 (仅 HTTP) 上的 HTTP API 监听器



所有监听器都绑定到所有可用接口。

检查节点使用的 TCP 监听器有助于发现非标准端口配置、应配置但未配置的协议插件（例如 MQTT）、节点被限制在仅少数几个网络接口上的情况等。如果某个端口不在监听器列表中，则意味着节点无法在其上接受任何连接。

## 检查服务器日志

RabbitMQ 节点会记录关键的客户端连接生命周期事件。TCP 连接必须成功建立，并且对端必须发送至少 1 个字节的数据，连接才会被视为已接受（并记录）。

从此开始，连接握手和协商将按照所使用的消息协议（例如 AMQP 0-9-1、AMQP 1.0 或 MQTT）的规范进行。

如果没有记录任何事件，这意味着要么没有成功的入站 TCP 连接，要么它们没有发送任何数据。

## 主机名解析

应用程序在连接 RabbitMQ 时使用主机名或带有主机名的 URI 非常普遍。dig 和 nslookup 是排查主机名解析问题的常用工具。

## 端口访问

除了主机名解析和 IP 路由问题外，TCP 端口无法进行外部连接也是客户端连接失败的常见原因。telnet 是一种常用的、非常简约的工具，用于测试与特定主机名和端口的 TCP 连接。

以下示例使用 `telnet` 连接到 `localhost` 的 `5672` 端口。在 `localhost` 上有一个运行默认配置的节点，且没有防火墙阻塞该端口，因此连接成功。随后输入 `12345` 并回车。这些数据将通过已打开的连接发送到节点。

由于 `12345` 不是正确的 AMQP 0-9-1 或 AMQP 1.0 协议头，因此服务器关闭了 TCP 连接。
    
    
    telnet localhost 5672  
    
    
    # => Trying ::1...  
    
    
    # => Connected to localhost.  
    
    
    # => Escape character is '^]'.  
    
    
    12345 # enter this and hit Enter to send  
    
    
    # => AMQP	Connection closed by foreign host.  
    

在 `telnet` 连接成功后，使用 `Control + ]` 然后输入 `quit`（或根据环境通过 `Control + D`）退出。

以下示例连接到 `localhost` 的 `5673` 端口。由于该端口上没有进程在监听，连接失败（被操作系统拒绝）。
    
    
    telnet localhost 5673  
    
    
    # => Trying ::1...  
    
    
    # => telnet: connect to address ::1: Connection refused  
    
    
    # => Trying 127.0.0.1...  
    
    
    # => telnet: connect to address 127.0.0.1: Connection refused  
    
    
    # => telnet: Unable to connect to remote host  
    

失败或超时的 `telnet` 连接强烈暗示存在代理、负载均衡器或防火墙阻塞了目标端口的入站连接。这也可能是因为目标节点上的 RabbitMQ 进程未运行，或使用了非标准端口。这些情况应在核对服务器监听器配置时予以排除。

有大量的防火墙、代理和负载均衡工具及产品。iptables 是 Linux 和其他类 UNIX 系统中常用的防火墙。网上有大量关于 `iptables` 的教程。

可以使用 netstat、ss、lsof 来检查节点的开放端口、TCP 和 UDP 连接。

以下示例使用 `lsof` 显示监听 5672 端口并使用 IPv4 的操作系统进程：
    
    
    sudo lsof -n -i4TCP:5672 | grep LISTEN  
    

同样，对于使用 IPv6 的程序：
    
    
    sudo lsof -n -i6TCP:5672 | grep LISTEN  
    

在 1883 端口上：
    
    
    sudo lsof -n -i4TCP:1883 | grep LISTEN  
    
    
    
    sudo lsof -n -i6TCP:1883 | grep LISTEN  
    

如果上述命令没有输出，则说明本地操作系统中没有进程监听该端口。

以下示例使用 `ss` 显示使用 IPv4 的监听 TCP 套接字及其操作系统进程：
    
    
    sudo ss --tcp -f inet --listening --numeric --processes  
    

同样，对于使用 IPv6 的 TCP 套接字：
    
    
    sudo ss --tcp -f inet6 --listening --numeric --processes  
    

有关 RabbitMQ 及其各种插件使用的端口列表，请参阅上文。通常，所有用于外部连接的端口都必须被防火墙和代理允许。

`rabbitmq-diagnostics listeners` 和 `rabbitmq-diagnostics status` 可用于列出 RabbitMQ 节点上启用的监听器及其端口。

## IP 路由

RabbitMQ 支持的消息协议使用 TCP，并要求客户端和 RabbitMQ 主机之间的 IP 路由功能正常。可以使用多种工具和技术来验证两台主机之间的 IP 路由。traceroute 和 ping 是许多操作系统上可用的两种常用选项。大多数路由表检查工具都是特定于操作系统的。

请注意，`traceroute` 和 `ping` 都使用 ICMP，而 RabbitMQ 客户端库和节点间连接使用 TCP。因此，仅凭 `ping` 成功并不能保证客户端连接一定成功。

`traceroute` 和 `ping` 都有基于其构建的 Web 工具和 GUI 工具。

## 流量捕获

所有网络活动都可以通过流量捕获进行检查、过滤和分析。

tcpdump 及其 GUI 版本 Wireshark 是捕获、过滤和分析流量的行业标准。两者都支持 RabbitMQ 支持的所有协议。请参阅在 RabbitMQ 中使用 Wireshark 指南以获取概述。

## TLS 连接

对于使用 TLS 的连接，有专门的TLS 排查指南。

采用 TLS 时，务必确保客户端使用正确的端口进行连接（见上文端口列表），并确保它们被配置为使用 TLS（执行 TLS 升级）。未配置使用 TLS 的客户端将成功连接到支持 TLS 的服务器端口，但随后会因为从未执行服务器预期的 TLS 升级而超时。

启用 TLS 的客户端连接到不支持 TLS 的端口时，会成功建立连接并尝试执行服务器不支持的 TLS 升级，从而触发协议解析异常。此类异常将被服务器记录。

## 检查连接

可以使用 netstat、ss、lsof 来检查节点的开放端口、TCP 和 UDP 连接。

以下示例使用 `netstat` 列出所有 TCP 连接套接字，无论其状态和接口如何。IP 地址将显示为数字而不是解析为域名。程序名称将打印在数字端口值旁边。
    
    
    sudo netstat --all --numeric --tcp --programs  
    

通过这种方式，可以检查入站（客户端、对等节点、CLI 工具）和出站（对等节点、Federation 链接和 Shovel）连接。

`rabbitmqctl list_connections` 和 管理 UI 可用于检查更多连接属性，其中一些是 RabbitMQ 或消息协议特定的：

  * 网络流量流向，包括入站和出站
  * 所使用的消息传递（应用层）协议
  * 连接的虚拟主机 (vhost)
  * 连接时间
  * 用户名
  * 通道 (Channel) 数量
  * 客户端库详细信息（名称、版本、功能）
  * 有效的心跳超时时间
  * TLS 详细信息



将管理 UI 或 CLI 工具的连接信息与 `netstat` 或 `ss` 的信息相结合，有助于排查行为异常的应用程序、应用实例和客户端库。

可以使用 Prometheus 和 Grafana 收集、聚合和监控大多数相关的连接指标。

## 检测连接高频变动（Connection Churn）

高连接变动（大量连接在短时间内创建和关闭）可能导致资源耗尽。因此，识别此类场景非常重要。`netstat` 和 `ss` 是检查 TCP 连接最常用的选项。处于 `TIME_WAIT` 状态的大量连接是高连接变动的一种典型征兆。处于 `ESTABLISHED` 以外状态的连接数量巨大，也是值得调查的征兆。

短寿命连接的证据可以在 RabbitMQ 日志文件中找到。例如，这是一个仅持续了几毫秒的连接示例：
    
    
    2018-06-17 16:23:29.851 [info] <0.634.0> accepting AMQP connection <0.634.0> (127.0.0.1:58588 -> 127.0.0.1:5672)  
    
    
    2018-06-17 16:23:29.853 [info] <0.634.0> connection <0.634.0> (127.0.0.1:58588 -> 127.0.0.1:5672): user 'guest' authenticated and granted access to vhost '/'  
    
    
    2018-06-17 16:23:29.855 [info] <0.634.0> closing AMQP connection <0.634.0> (127.0.0.1:58588 -> 127.0.0.1:5672, vhost: '/', user: 'guest')
