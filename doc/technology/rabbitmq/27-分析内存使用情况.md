# 关于内存占用的推理

## 概述

运维人员需要能够分析节点的内存使用情况，包括绝对值和相对值（“什么占用了最多的内存”）。这是系统监控的一个重要方面。

本指南重点介绍如何分析 RabbitMQ 节点的报告（监控）内存占用情况，包括内核页缓存部分。理解这一点对于流 (streams) 和分区流 (partitioned streams) 的场景非常重要。

本文档附带了一些密切相关的指南：

  * 内存报警阈值
  * 资源告警



RabbitMQ 提供了多种工具来报告和分析节点的内存使用情况：

  * `rabbitmq-diagnostics memory_breakdown`
  * `rabbitmqadmin show memory_breakdown_in_percent` 和 `rabbitmqadmin show memory_breakdown_in_bytes`
  * `rabbitmq-diagnostics observer` 提供了非常细粒度、基于 Erlang 进程级别的内存消耗视图
  * 基于 Prometheus 和 Grafana 的监控使得观察内存随时间变化的分布成为可能
  * 管理 UI 在节点页面上提供了与 `rabbitmq-diagnostics status` 相同的分布情况
  * HTTP API 提供了与管理 UI 相同的信息，这对监控非常有用
  * rabbitmq-top 和 `rabbitmq-diagnostics observer` 提供了类似于 top 命令的、更细粒度的 Erlang 进程视图



在推理节点内存使用情况时，获取节点内存分布应作为第一步。

请注意，所有测量值都是近似的，基于底层运行时或内核在特定时间点（通常在 5 秒时间窗口内）返回的值。

## 在容器和 Kubernetes 上运行 RabbitMQ

当 RabbitMQ 运行在使用 cgroups 的环境中（即各种容器化环境和 Kubernetes）时，必须考虑与内存限制和内核页缓存相关的某些方面，特别是在使用流和超级流的集群中。

## 内存使用分布

RabbitMQ 节点可以报告其内存使用分布。该分布以类别列表（如下所示）及其对应类别的内存占用量形式提供。

每个类别是该类型所有进程或表的运行时报告内存占用量的总和。这意味着“连接”类别是所有连接进程所用内存的总和，“通道”类别是所有通道进程所用内存的总和，“ETS 表”是节点上所有内存表所用内存的总和，依此类推。

### 内存分布是如何工作的

内存使用分布报告了目标节点上按类别划分的已分配内存分布情况。

  * 连接（进一步拆分为四类：读取器、写入器、通道、其他）
  * 仲裁队列 (Quorum queue) 副本
  * 流 (Stream) 副本
  * 经典队列消息存储和索引
  * 二进制堆引用
  * 节点本地指标（管理插件状态数据库）
  * 内部模式数据库表
  * 插件，包括传输消息的协议（如 Shovel 和 Federation）及其内部队列
  * 已分配但尚未使用的内存
  * 代码（字节码、模块元数据）
  * ETS（内存键值存储）表
  * 原子表 (Atom tables)
  * 其他



通常类别之间没有重叠（同一内存不会被重复计算）。插件和运行时版本可能会影响这一点。

## 内存分布类别

### 连接

这包括客户端连接（包括 Shovels 和 Federation 链接）及其通道所使用的内存，以及传出连接（Shovels 和 Federation 上游链接）。大部分内存通常被 TCP 缓冲区占用，在 Linux 上，默认情况下 TCP 缓冲区会自动调整为约 100 kB。可以降低 TCP 缓冲区大小，但会以连接吞吐量成比例降低为代价。有关详细信息，请参阅网络指南。

通道也会消耗内存。通过优化应用程序使用的通道数量，可以减少该内存占用量。可以使用 `channel_max` 配置设置来限制连接上的最大通道数。
    
    
    channel_max = 16  
    

请注意，一些构建在 RabbitMQ 客户端之上的库和工具可能会隐式需要一定数量的通道。找到一个最优值通常需要反复试验。

### 队列和消息

由队列、队列索引、队列状态使用的内存。排队的消息将部分归入此类。

当处于内存压力下时，队列会将内容交换到磁盘。确切的行为取决于队列属性、客户端发布的消息是持久的还是临时的，以及节点的持久化配置。

消息体不会出现在这里，而是出现在“二进制数据 (Binaries)”中。

### 消息存储索引

默认情况下，消息存储使用所有消息的内存索引，包括那些分页到磁盘的消息。插件允许用基于磁盘的实现替换它。

### 插件

由插件使用的内存（Erlang 客户端计算在“连接”类别下，管理数据库单独计算）。此类将包含一些用于协议插件（如 STOMP 和 MQTT）的每个连接内存，以及由插件（如 Shovel 和 Federation）排队的消息。

### 预分配内存

由运行时（VM 分配器）预分配但尚未使用的内存。下面将更详细地介绍这一点。

### 内部数据库

内部数据库 (Mnesia) 表保留其所有数据的内存副本（即使在磁盘节点上也是如此）。通常只有在存在大量队列、交换机、绑定、用户或虚拟主机时才会很大。插件也可以将数据存储在同一个数据库中。

### 管理（统计）数据库

统计数据库（如果启用了管理插件）。在集群中，大多数统计信息本地存储在节点上。集群中聚合统计信息所需的跨节点请求可能会被缓存。缓存的数据将报告在此类别中。

### 二进制数据

运行时中共享二进制数据使用的内存。该内存的大部分是消息体和元数据。

对于某些工作负载，二进制数据堆可能很少进行垃圾回收。`rabbitmqctl force_gc` 可用于强制执行回收。以下命令强制执行回收并报告释放最多二进制堆引用的顶级进程：
    
    
    rabbitmqctl eval 'recon:bin_leak(10).'  
    
    
      
    
    
    rabbitmqctl force_gc  
    

对于不提供 `rabbitmqctl force_gc` 的 RabbitMQ 版本，请使用：
    
    
    rabbitmqctl eval 'recon:bin_leak(10).'  
    
    
      
    
    
    rabbitmqctl eval '[garbage_collect(P) || P <- processes()].'  
    

### 其他 ETS 表

除统计数据库和内部数据库表之外的其他内存表。

### 代码

由代码使用的内存（字节码、模块元数据）。该部分通常相当稳定且相对较小（除非节点完全空白且不存储任何数据）。

### 原子

原子使用的内存。应该相当稳定。

### 使用 rabbitmq-top 进行进程级分析

rabbitmq-top 是一个插件，有助于识别消耗大部分内存或调度程序 (CPU) 时间的运行时进程（“轻量级线程”）。

该插件随 RabbitMQ 一起发布。通过以下命令启用它：
    
    
    [sudo] rabbitmq-plugins enable rabbitmq_top  
    

该插件将新的管理选项卡添加到管理 UI。一个选项卡显示按以下指标排序的顶级进程：

  * 已用内存
  * 还原 (Reductions)（调度程序/CPU 消耗单位）
  * Erlang 邮箱长度
  * 对于 `gen_server2` 进程，内部操作缓冲区长度



第二个选项卡显示 ETS（内部键值存储）表。这些表可以按已用内存量或行数进行排序。

## 预分配内存

Erlang 内存分布报告仅为当前正在使用的内存，而不包括已分配以备后用或由操作系统保留的内存。像 `ps` 这样的 OS 工具报告的内存使用量可能比运行时报告的要多。

此内存包括已分配但未使用的内存，以及操作系统未分配但保留的内存。这两个值都取决于操作系统和 Erlang VM 分配器设置，并且可能会有显著波动。

这两个部分的计算方式取决于 `vm_memory_calculation_strategy` 设置。如果策略设置为 `erlang`，则不会报告未使用内存。如果内存计算策略设置为 `allocated`，则不会报告操作系统保留的内存。因此，`rss` 是从内核和运行时提供最多信息的策略。

当节点在长时间运行后报告大量已分配但未使用的内存时，这可能是运行时内存碎片化的标志。不同的分配器设置组合可以减少碎片并提高内存利用率。正确的设置取决于工作负载和消息载荷大小的分布。

运行时的内存分配器行为可以进行调优，请参考运行时指南、erl 和 erts_alloc 文档。

## 内核页缓存

除了 RabbitMQ 节点直接分配和使用的内存外，该节点读取的文件还可以由操作系统进行缓存。此缓存提高了 I/O 操作效率，并且在操作系统检测到可用内存百分比较低时会被逐出（清除）。

使用 RabbitMQ 流的工作负载通常会导致较大的内核页缓存大小，特别是在消费者访问跨越数天或数周的消息时。

重要

一些监控工具不将页缓存大小包含在进程监控指标中。其他工具则将其添加到进程的常驻集大小 (RSS) 占用中。这可能会导致混淆：**页缓存不由 RabbitMQ 节点维护或控制。它由操作系统内核维护、控制和逐出（清除）。**

这在基于 Kubernetes 的部署中尤为常见（如果不使用 cgroup v2），且运行的 RabbitMQ 使用基于使用 cgroups v1 的旧版本发行版的容器镜像。

强烈建议使用 Kubernetes 1.25.0（或更高版本）及以下发行版，因为它们对内核页缓存内存核算采用了更合理的方法：

  * CentOS Stream 9 或更高版本
  * Fedora 31 或更高版本
  * Ubuntu 21.10 或更高版本
  * Debian 11 Bullseye 或更高版本



从 4.12 版本开始的 Red Hat OpenShift 基于 Kubernetes 1.25（或更高版本）。

### 较大的页缓存大小说明了什么工作负载特征？

通常，较大的页缓存大小仅表明工作负载是 I/O 密集型的，并且可能使用了大数据集的流。这并不表示节点存在内存泄漏：当内核检测到系统可用内存不足时，缓存会被内核清除。

### 在非容器化环境（虚拟机或物理机）中检查页缓存

在非容器化环境中（例如在虚拟机或裸机上运行的 RabbitMQ 节点），请使用：
    
    
    cat /proc/meminfo | grep -we "Cached"  
    

来检查内核页缓存的大小。

### 在容器化环境中检查页缓存大小

在 Kubernetes 等容器化环境中，可以使用以下两个 `/sys` 伪文件系统路径来检查 RSS 和页缓存占用量：
    
    
    cat /sys/fs/cgroup/memory/memory.stat  
    
    
    cat /sys/fs/cgroup/memory/memory.usage_in_bytes  
    

两个关键指标分别命名为 `rss`（常驻集大小）和 `cache`（页缓存）。

## 内存使用监控

建议生产系统监控所有集群节点的内存使用情况，最好结合基础设施级指标进行细分监控。通过将细分类别与其他指标（例如并发连接数或排队消息数）相关联，可以检测由特定应用程序行为引起的问题（例如连接泄漏或没有消费者的队列不断增长）。

## 队列内存

### 消息使用多少内存？

消息有多个部分会消耗内存：

  * 载荷 (Payload)：>= 1 字节，大小可变，通常为几百字节到几百千字节
  * 协议属性：>= 0 字节，大小可变，包含头信息、优先级、时间戳、回复地址等。
  * RabbitMQ 元数据：>= 720 字节，大小可变，包含交换机、路由键、消息属性、持久性、重投递状态等。
  * RabbitMQ 消息排序结构：16 字节



一旦考虑到属性和元数据，带有 1KB 载荷的消息将使用 2KB 的内存。

一些消息可以存储在磁盘上，但其元数据仍保留在内存中。

### 队列使用多少内存？

每个队列由一个 Erlang 进程支持。如果队列是副本化的，则每个副本都是在不同集群节点上运行的独立 Erlang 进程。

由于队列的每个副本（无论是领导者还是追随者）都是单个 Erlang 进程，因此可以保证消息排序。多个队列意味着多个 Erlang 进程，它们获得均匀的 CPU 时间。这确保了一个队列不会阻塞其他队列。

单个队列的内存使用情况可以通过 HTTP API 获取：
    
    
    curl -s -u guest:guest http://127.0.0.1:15672/api/queues/%2f/queue-name |  
    
    
      python -m json.tool  
    
    
      
    
    
    {  
    
    
        ..  
    
    
        "memory": 97921904,  
    
    
        ...  
    
    
        "message_bytes_ram": 2153429941,  
    
    
        ...  
    
    
    }  
    

  * `memory`：队列进程使用的内存，计入消息元数据（每条消息至少 720 字节），不计入超过 64 字节的消息载荷。
  * `message_bytes_ram`：消息载荷使用的内存，与大小无关。



如果消息较小，消息元数据可能比消息载荷使用更多的内存。10,000 条带有 1 字节载荷的消息将使用 10KB 的 `message_bytes_ram`（载荷）和 7MB 的 `memory`（元数据）。

如果消息载荷较大，它们将不会反映在队列进程内存中。10,000 条带有 100 KB 载荷的消息将使用 976MB 的 `message_bytes_ram`（载荷）和 7MB 的 `memory`（元数据）。

### 为什么队列内存在发布/消费时会增加和减少？

Erlang 为每个 Erlang 进程使用分代垃圾回收。垃圾回收是按队列执行的，独立于所有其他 Erlang 进程。

当垃圾回收运行时，它会在取消分配未使用的内存之前复制已使用的进程内存。这可能导致队列进程在垃圾回收期间使用高达两倍的内存，如下图所示（队列包含大量消息）：

### 垃圾回收期间的队列内存增长是一个问题吗？

如果 Erlang VM 尝试分配的内存超过可用内存，VM 本身将崩溃或被 OOM killer 杀死。当 Erlang VM 崩溃时，RabbitMQ 将丢失所有非持久数据。

垃圾回收可能会短暂地使队列使用的内存加倍。然而，考虑到：

  * 垃圾回收过程在不同时间针对不同的队列执行
  * 而且在现代 RabbitMQ 版本中，所有类型的队列（经典、仲裁、流）要么根本不将消息存储在内存中，要么只在内存中存储有限数量的消息



由垃圾回收过程引起的 RabbitMQ 节点整体内存使用的显著峰值是非常不可能的。

## 总内存使用计算策略

RabbitMQ 可以使用不同的策略来计算节点的内存使用量。从历史上看，节点从运行时获取此信息，报告已使用的内存（不仅是已分配的）。这种被称为 `legacy`（`erlang` 的别名）的策略往往会低估，不建议使用。

有效策略使用 `vm_memory_calculation_strategy` 键进行配置。有两个主要选项：

  * `rss` 使用 OS 特定的方法查询内核以查找节点 OS 进程的 RSS（常驻集大小）值。此策略最精确，是 Linux、MacOS、BSD 和 Solaris 系统上的默认策略。使用此策略时，RabbitMQ 每秒运行一次短暂的子进程。

  * `allocated` 是一种查询运行时内存分配器信息的策略。它通常非常接近 `rss` 策略报告的值。这是 Windows 上的默认策略。




`vm_memory_calculation_strategy` 设置也会影响内存分布报告。如果设置为 `legacy` (`erlang`) 或 `allocated`，则不会报告某些内存分布字段。本指南后面将更详细地介绍这一点。

以下配置示例使用 `rss` 策略：
    
    
    vm_memory_calculation_strategy = rss  
    

同样，对于 `allocated` 策略，请使用：
    
    
    vm_memory_calculation_strategy = allocated  
    

要查找节点使用的策略，请参阅其有效配置。
