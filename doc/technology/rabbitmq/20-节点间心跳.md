# 节点间通信心跳 (Net Tick Time)

## 概述

本指南介绍了 RabbitMQ 节点和 CLI 工具（实际上是 Erlang 节点）用于确定对等方是否可用的一种机制，即 `"net ticks"` 或 `kernel.net_ticktime`。

集群中的每一对节点都通过传输层相连。所有节点对之间会定期交换 tick 消息，以维护连接并检测断开情况。否则，网络中断可能在相当长的一段时间内无法被察觉（具体取决于传输层和操作系统内核设置，例如 TCP 设置）。从根本上讲，这与消息传递协议中 心跳 旨在解决的问题相同，只是对象不同：即 RabbitMQ 集群节点和 CLI 工具。

节点和已连接的 CLI 工具会定期向对方发送小型数据帧。如果在给定的时间段内没有从对等方接收到任何数据，则该对等方被视为不可用（"down"）。

当某个 RabbitMQ 节点确定另一个节点已宕机时，它会记录一条消息，给出对方节点的名称及原因，例如
    
    
    2018-11-22 10:44:33.654 [info] node rabbit@peer-hostname down: net_tick_timeout  
    

在这种情况下，`net_tick_timeout` 事件告诉我们，由于超过了 net ticktime，对方节点被检测为宕机。另一个常见原因是 `connection_closed`，意味着连接在 TCP 层被显式关闭。

Erlang 文档 包含有关此子系统的更多详细信息。

## Tick 频率

Tick 消息的频率和故障检测由 `net_ticktime` 配置设置控制。通常，每对节点在 `net_ticktime` 秒内会交换四次 tick。如果在 `net_ticktime`（± 25%）秒内未从节点收到任何通信，则该节点被视为已宕机，不再是集群的一员。

增加集群中所有节点的 `net_ticktime` 会使集群对短期网络中断更具弹性，但剩余节点检测到已崩溃节点所需的时间会更长。相反，减少集群中所有节点的 `net_ticktime` 会降低检测延迟，但会增加检测到虚假 网络分区 的风险。

更改默认的 `net_ticktime` 所带来的影响应仔细考虑。集群中的所有节点必须使用相同的 `net_ticktime`。以下示例 advanced.config 配置演示了将默认的 `net_ticktime` 从 60 秒增加到 120 秒：
    
    
    [  
    
    
      {kernel, [{net_ticktime,  120}]}  
    
    
    ].  
    

## 对 HTTP API 的影响

HTTP API 通常需要执行全集群范围的查询，这会导致在检测到并处理分区之前，UI 可能看起来没有响应。降低 `net_ticktime` 有助于改善此类事件期间的响应能力，但如上所述，更改 `net_ticktime` 的任何决定都应谨慎执行。

## Windows 配置

由于 RabbitMQ 作为 Windows 服务启动的方式，您不能直接使用配置文件来设置 `net_ticktime`。请参阅 Windows 配置 文档中的 此章节，了解在将 RabbitMQ 作为 Windows 服务运行时如何设置 `net_ticktime`。
